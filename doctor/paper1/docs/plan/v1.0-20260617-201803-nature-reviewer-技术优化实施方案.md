# Nature 风格评审后技术优化实施方案

版本：v1.0  
时间戳：20260617-201803  
依据文档：`docs/nature_reviewer_report.md`  
适用范围：`doctor/paper1` 论文、实验、复现脚本与中英文稿件  

## 1. 目标与判断

本方案面向《Confidence-Aware Edge Routing for Robotic TCM Tongue Imaging》当前仓库状态，回应 Nature 风格评审中最核心的质疑：真实网络证据不足、真实退化建模不足、B2 与 B3/B4 的价值取舍不充分、M2 尚未闭环到下游诊断效用、物理重采样本量偏小，以及跨场景推广性不足。

当前不建议继续把 B2 叙述为单一最优主线。更稳妥的主张应调整为：

> 本文提出一个可审计的置信度感知机器人采集路由框架；B2 是 CPU-only、低延迟、可解释部署档，B3/B4 是高有效帧率档，最终部署应由网络条件、边缘算力和临床质量权重共同选择。

技术实现上，优化重点不是再堆一个更强 IQA 模型，而是补齐证据链：把“仿真延迟 + 合成模糊 + 内部 M2”扩展为“真实/可控网络实测 + 真实或物理化退化 + 下游诊断效用 + 机器人重采前后质量变化”。

### 2.2 必须修正的现状问题

1. `latex/sections/05_6_extended_analysis.tex` 中存在与当前全量结果不一致的表述，例如 “B2 M2 remains at 1.000” 和 “M1 p50 341--348 ms”。当前全量结果应以 `docs/验证结果_全量.md` 和 `table_ii.json` 为准：B2 M2 为 0.604，M1 p50 约 208.3 ms。
2. `Closed-Loop Acquisition` 容易被控制领域审稿人理解为低层控制闭环。应统一改为 `task-level closed-loop routing/acquisition`，并明确不干涉 Franka 1 kHz 底层控制。
3. B2 作为“primary deployable path”的理由目前主要是低延迟和可解释，但 B3/B4 在 M2 上差距过大。需要用效用函数或部署档位取代主观选择。
4. M2 是内部质量门控指标，不是临床标签或下游诊断准确率。所有临床效用相关表述必须降级为“proxy”，并新增下游评估。

### WP1：真实/可控网络实测轨道

目标：新增一个与主仿真矩阵并列的 `measured-network track`，用于回答真实 WAN/丢包/抖动下路由是否仍有价值。

建议新增产物：

| 类型 | 路径建议 | 说明 |
|------|----------|------|
| 配置 | `doctor/paper1/experiments/configs/wan_measured.yaml` | 网络场景、帧数、baselines、远端 URL |
| 脚本 | `doctor/paper1/experiments/run_wan_measured.py` | 调用真实 HTTP cloud stub，记录 monotonic timing |
| 云端 stub | `doctor/paper1/sim/cloud_stub.py` | FastAPI 或标准库 HTTP 服务，返回固定 payload |
| netem 工具 | `scripts/paper1_run_wan_netem.sh` | 添加/清理 `tc netem`，运行实验 |
| 结果 | `doctor/paper1/experiments/results/wan_measured_*.csv` | 每帧 RTT、loss、retry、decision |
| 报告 | `doctor/paper1/experiments/results/wan_measured_summary.json` | p50/p95/p99、成功率、排序稳定性 |
| 表格 | `doctor/paper1/latex/sections/table_wan_measured.tex` | 新增正文或附录表 |

实验矩阵建议：

| 场景 | 网络设置 | 帧数 |
|------|----------|------|
| LAN baseline | 无 netem，localhost 或内网机器 | 3 seeds × 100 |
| mild WAN | delay 50 ms, jitter 10 ms, loss 0% | 3 seeds × 100 |
| clinic WAN | delay 150 ms, jitter 30 ms, loss 1--5% | 3 seeds × 100 |
| stressed WAN | delay 300 ms, jitter 80 ms, loss 10% | 3 seeds × 100 |
| failure stress | delay 500 ms, jitter 120 ms, loss 20% | 1 seed × 100，附录即可 |

技术细节：

1. 使用 `time.monotonic_ns()` 记录每段耗时，避免系统时钟漂移。
2. 每帧 JSONL/CSV 至少记录：
   - `trial_id`
   - `baseline`
   - `seed`
   - `network_profile`
   - `q_img`
   - `route_decision`
   - `retry_count`
   - `http_status`
   - `upload_attempts`
   - `rtt_measured_ms`
   - `latency_capture_ms`
   - `latency_iqa_ms`
   - `latency_route_ms`
   - `latency_upload_ms`
3. 报告不只写 B2 快，而要写排序稳定性：
   - B2 vs B0 的 p50/p95 RTT 差异；
   - B2/B4 在不同 loss 下的有效帧率与上传成功率；
   - 模拟 RTT 与实测 RTT 的 Spearman 相关或 rank agreement。
4. 若没有真实远端服务器，netem 本地实测仍可作为“controlled network impairment”，但文稿必须如实写 `controlled netem`，不能写成真实医院 WAN。

验收标准：

| 指标 | 最低要求 |
|------|----------|
| 实测规模 | 至少 4 个网络 profile，每个 profile 3 seeds × 100 帧 |
| 日志完整性 | 每帧有 JSONL/CSV timing，可复算表格 |
| 结论稳健性 | 至少报告 B2/B4 相对 B0 在 p50/p95 下的排序是否保持 |
| 文稿呈现 | 新增 `Measured network track` 小节，明确与 Table II 仿真分离 |

### WP2：真实或物理化图像退化集

目标：把“高斯模糊是否代表真实运动模糊”的质疑转化为可测问题。

建议分两阶段做：

阶段 A：物理化合成退化，快速完成。

1. 在现有 Gaussian blur 基础上加入：
   - 方向运动模糊 kernel：长度 5/9/13/17 px，角度 0/30/60/90/120/150 度；
   - defocus disk blur；
   - 局部 specular highlight；
   - under/over exposure；
   - mixed degradation：motion + exposure。
2. 新增脚本：
   - `doctor/paper1/scripts/synth_motion_degrade.py`
   - `doctor/paper1/experiments/edge_iqa/evaluate_degradation_stress.py`
3. 输出：
   - `experiments/results/degradation_stress.csv`
   - `experiments/results/degradation_stress_summary.json`
   - `latex/sections/table_degradation_stress.tex`

阶段 B：小规模真实退化采集，作为强证据。

1. 采集 n>=200 对 ROI 样本：
   - 清晰采集；
   - 患者/假体轻微运动；
   - FR3/相机轻微扫动；
   - 光照不足；
   - 强反光。
2. 每张图由两名标注者给出质量标签：
   - `clear`
   - `motion_blur`
   - `defocus`
   - `poor_exposure`
   - `specular`
   - `unusable`
3. 记录采集条件：
   - 机器人 pose 或相机距离；
   - 曝光参数；
   - 光源档位；
   - 是否触发重采 skill。
4. 新增清单：
   - `doctor/paper1/data/real_degradation/manifest.csv`
   - 原图不进入公开仓库时，仅保存脱敏 ROI 或 hash + 路径占位。

评价指标：

| 指标 | 说明 |
|------|------|
| Edge-IQA AUC/F1 | 二分类 clear vs unusable |
| B3/B4 AUC/F1 | 学习型/混合门控对真实退化是否更稳 |
| Failure taxonomy | 哪类退化最容易误判 |
| Q uplift | 重采前后 `q_img` 是否提高 |

验收标准：

| 项 | 最低要求 |
|----|----------|
| 物理化 stress test | 至少 5 类退化，输出 summary JSON 和 LaTeX 表 |
| 真实退化小集 | n>=200，若无法采集真实患者，则使用舌模/志愿者脱敏 ROI，并说明限制 |
| 文稿呈现 | 新增真实退化或 stress-test 小节，明确 Gaussian-only 结果的边界 |

### WP3：B2/B3/B4 效用函数与部署档位

目标：正面回答“为什么 M2 只有 0.604 的 B2 还能作为主线”的问题。

建议将主张改为多档策略：

| 档位 | 推荐策略 | 使用条件 | 叙事定位 |
|------|----------|----------|----------|
| Tier-A | B2 | CPU-only、无 GPU、强可解释、低功耗 | 低延迟部署基线 |
| Tier-B | B4 | 有轻量 NN runtime，希望保留曝光规则可解释性 | 推荐高质量混合档 |
| Tier-C | B3/NIQE/BRISQUE | 离线质控或算力充足 | 高有效率但成本高 |
| Tier-D | B2u | 需要自动权衡 latency/validity | 研究型自适应策略 |

效用函数建议：

```text
U(policy | profile) =
  w_valid * M2
  - w_latency * normalized(M1_p50)
  - w_tail * normalized(M1_p95)
  - w_compute * edge_cost_ms
  - w_audit * audit_penalty
```

典型 profile：

| Profile | 权重倾向 | 预期选择 |
|---------|----------|----------|
| `cpu_low_power` | 高 `w_latency`、高 `w_compute`、高 `w_audit` | B2 |
| `clinical_quality` | 高 `w_valid`、高 `w_tail` | B4 或 B3 |
| `unstable_wan` | 高 `w_tail`、高 loss penalty | 需实测后决定 |
| `offline_triage` | 低 `w_latency`、高 `w_valid` | B3/NIQE |

实现建议：

1. 复用已有 `langgraph_router/utility_route.py` 和 quick 结果中的 B2u 思路，扩展到全量矩阵。
2. 新增：
   - `experiments/configs/utility_profiles.yaml`
   - `experiments/run_utility_matrix.py`
   - `experiments/reports/build_utility_table.py`
   - `latex/sections/table_utility_profiles.tex`
3. 输出每个 profile 的最优策略和 sensitivity：
   - `w_valid` 从 0.2 到 0.9 扫描；
   - 找出 B2 与 B4 切换边界；
   - 画 `fig_utility_frontier.pdf`。

验收标准：

| 项 | 通过标准 |
|----|----------|
| 决策透明 | 能解释在哪些条件下选 B2，哪些条件下选 B4 |
| 不与数据冲突 | 不再把 B2 说成质量最优 |
| 全量验证 | 至少在 3 seeds × 500 帧上给出 utility profile 表 |
| 文稿更新 | 引言、结果、讨论同步改为 tiered routing 叙事 |

### WP4：下游诊断效用 M7

目标：把内部 M2 指标连接到下游 TCM 图像理解任务，避免“为了自圆其说定义指标”的质疑。

建议新增指标：

| 指标 | 定义 |
|------|------|
| M7-Acc | 下游舌象条件分类准确率 |
| M7-Conf | 正确类别平均置信度 |
| M7-ECE | Expected calibration error |
| M7-Reject | 被 Edge-IQA 拒绝帧的下游置信度是否更低 |
| M7-Delta | 路由前后 Acc/Conf 的差值 |

实现方案：

1. 先用 ShezhenV3 十类 condition label 做非临床诊断 proxy，避免过度医疗 claim。
2. 新增轻量分类器：
   - `doctor/paper1/experiments/tcm_condition/train_condition_classifier.py`
   - `doctor/paper1/experiments/tcm_condition/evaluate_routing_m7.py`
3. 评价路径：
   - 原始 test frames；
   - Gaussian/physical degradation frames；
   - B0 上传集合；
   - B2 接受集合；
   - B4 接受集合；
   - B2/B4 拒绝集合。
4. 核心分析：
   - accepted frames 是否有更高 Acc/Conf；
   - rejected frames 是否更容易低置信或误分类；
   - B2 的低 M2 是否会漏掉临床可用图像；
   - B4 的高 M2 是否真正提升下游稳定性。

文稿边界：

不要写“提升临床诊断准确率”。建议写：

> We evaluate downstream condition-classifier confidence as a non-clinical proxy for whether routing removes visually unreliable inputs.

验收标准：

| 项 | 最低要求 |
|----|----------|
| 分类器 | 固定 train/val/test，保存 checkpoint 和 meta |
| 对照 | B0/B2/B4 至少三组 |
| 统计 | paired bootstrap CI 或 McNemar/置换检验 |
| 文稿 | 新增 M7 表或附录表，明确其为 proxy |

### WP5：Franka 物理重采扩大验证

目标：把当前 n=50 的辅助轨从“路由耗时可跑”升级为“重采动作能改善质量”的物理证据。

当前 `franka_m6_summary.json` 只报告本地 RTT p50/p95，无法回答重采是否提升图像质量。需要新增 pre/post 质量字段。

新增 JSONL 字段建议：

| 字段 | 说明 |
|------|------|
| `q_before` | 重采前 Edge-IQA |
| `q_after` | 重采后 Edge-IQA |
| `delta_q` | `q_after - q_before` |
| `skill_name` | `adaptive_visual_damping` 或 `exposure_loop_tuning` |
| `skill_duration_ms` | 实际 skill 耗时 |
| `pose_delta_norm` | 机器人末端位姿变化量 |
| `exposure_before/after` | 相机曝光/增益 |
| `operator_flag` | 是否人工干预 |

实验设计：

| 子集 | n | 目的 |
|------|---|------|
| blur recovery | >=100 | 验证 `adaptive_visual_damping` 或姿态微调对 Q 的影响 |
| exposure recovery | >=60 | 验证 `exposure_loop_tuning` |
| mixed failure | >=40 | 观察失败模式 |
| normal clear | >=100 | 估计误触发率 |

分析输出：

1. `experiments/results/franka_resample_quality.csv`
2. `experiments/results/franka_resample_quality_summary.json`
3. `figures/fig_s2_franka_delta_q.pdf`
4. `latex/sections/table_franka_resample.tex`

验收标准：

| 项 | 最低要求 |
|----|----------|
| 样本量 | 总 n>=300，至少 n>=200 涉及真实重采 |
| 质量改善 | 报告 `delta_q` median、IQR、bootstrap CI |
| 失败分析 | 至少列出 top-3 失败模式 |
| 控制边界 | 明确仍是任务级重采，不进入 1 kHz 控制环 |

### WP6：跨场景泛化与方法论抽象

目标：把论文从“舌诊工程项目”提升为“置信度感知机器人视觉采集路由方法”。

建议新增一张 architecture transfer table：

| 场景 | ROI/质量信号 | 重采 skill | 云端任务 | 需替换模块 |
|------|--------------|------------|----------|------------|
| TCM tongue imaging | 舌 ROI、blur/exposure | 姿态/曝光重采 | 舌象 condition proxy | 当前实现 |
| Endoscopy snapshot | 病灶 ROI、specular/blur | 镜头冲洗/停帧 | 病灶分类 | scorer + skill map |
| Surface inspection | 零件 ROI、focus/lighting | 光源角度/相机距离 | 缺陷检测 | scorer + robot pose |
| Wound imaging | 创面 ROI、color constancy | 光照/距离调整 | 分割/面积估计 | scorer + calibration |

实现上不必立即做完整新数据集，但要把系统抽象清楚：

1. 定义 `QualityScorer` 接口：
   - `score(image, roi) -> q_img, flags`
2. 定义 `RecoverySkillMap`：
   - `flags -> skill_name, params`
3. 定义 `RoutingPolicy`：
   - `state -> upload/resample/fail_safe`
4. 在文稿中用 TCM 作为实例化，而不是唯一适用范围。

验收标准：

| 项 | 通过标准 |
|----|----------|
| 方法抽象 | 系统章节能脱离 TCM 单独成立 |
| 迁移表 | 至少 3 个非 TCM 场景 |
| 不夸大 | 明确哪些模块必须重标定或替换 |
